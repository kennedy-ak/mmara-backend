MIGRATION PLAN: pypdf -> LlamaParse + ChromaDB -> Pinecone
============================================================

CONTEXT
-------
MMara's current PDF extraction uses pypdf, which produces basic text that often
mangles tables, headers, and legal formatting. Replacing it with LlamaParse
(AI-powered extraction) will produce much cleaner, structure-aware text -- the
single biggest accuracy improvement. Replacing ChromaDB with Pinecone moves the
vector DB to a managed cloud service with better scalability. The local
MiniLM-L6-v2 embedding model stays (free, no API cost). Existing section-based
chunking logic stays.

KEY DESIGN DECISIONS
====================
1. Text stored in Pinecone metadata -- Pinecone has no "documents" field like
   ChromaDB; chunk text goes in metadata["text"] (40KB limit, our chunks are
   ~512 chars)
2. ChromaDB-compatible search() return format -- keeps
   RetrievalService._semantic_search() working without changes
3. LlamaParse markdown output -- preserves headings/structure that the existing
   section regex patterns can match
4. Lazy BM25 build -- BM25 index rebuilds on first search after invalidation


VERIFICATION PLAN
=================

2. Install deps: pip install llama-parse "pinecone[grpc]" (and remove old ones)
3. Test extraction: Upload a test PDF via POST /api/v1/admin/documents, then

4. Test retrieval: Use POST /api/v1/admin/retrieve with a legal query -- verify

5. Test chat: Send a message via POST /api/v1/chat/message -- verify the full

6. Test stats: GET /api/v1/admin/stats -- verify document/chunk counts reflect

7. Test deletion: Delete a document via DELETE /api/v1/admin/documents/{id} --
   verify chunks are removed from Pinecone


POTENTIAL RISKS
===============
- LlamaParse rate limits: Free tier has limited pages/day; bulk re-indexing may
  need batching
- Markdown section patterns: LlamaParse markdown may prefix headers with # --
  if section detection breaks, add "^#{1,3}\s*Section\s+\d+" patterns to
  section_patterns list
- BM25 cold start: First search after restart fetches ALL vectors from
  Pinecone -- could be slow for large collections
- Pinecone metadata types: Must be str/int/float/bool/list[str] --
  sanitization logic handles this
